# Decisions Log

Format: date, decision, reasoning. Append only, never edit past entries, add a new entry if a decision changes.

## 2025-11
Project starts as a citizen-reporting app for urban waste blackspots (v0.1). B2B2C model: citizens report, municipal managers use the data.

## 2026 H1
v0.1 evolves into v0.2, a React and Firebase app with the same B2B2C model.

## 2026-07, AddVenture acceleration, CITIC
Structural flaw identified in the B2B2C model: no citizen data means no value for managers, no revenue means no way to attract citizens, a deadlock. Pivot decided: v0.3, an automated B2B pipeline built on scraped and public data, removing the dependency on citizen participation entirely. Independence from the audited operator becomes the explicit differentiator against IoT incumbents.

## 2026-07-09
Demo day at AddVenture, CITIC, A Coruna. v0.3 presented as a pipeline concept and pitch deck, not a running build.

## 2026-08-17
Project reopened as a portfolio and technical study, not for active sale or commercialization. v0.3 build plan changes from polishing v0.2 to a fresh, incremental build across Etapas 0 to 6, starting from an empty repository, no application code carried over from v0.2.

## 2026-08-20
Etapa 0 closed. Real risks fixed: an open Firestore write rule with no authentication, and an Anthropic API key committed in March, revoked and purged from git history. A prior assumption, a Firestore rules expiry date, is corrected, that was never the actual risk.

No login cookie or session token was present in the scraped output, checked directly against the export file rather than assumed.

## 2026-09-03
Two modeling decisions taken while consolidating the Etapa 4 query list, full reasoning in `docs/queries.md`. First, coordinate is stored as a plain attribute on the record, `lat` and `lng` directly on the record, not as a separate place entity with its own identity; normalising place into a joined table or collection was considered and rejected. Second, the report's unit of analysis is both zona and point, with zona as the primary aggregation unit, matching the 4.7 hotspot by zone framing and the verification report deliverable, and point level precision kept as a secondary need for map display and any future radius based feature.

## 2026-09-04
Field level consequence of the 2026-09-03 coordinate decision settled: the record carries `lat`, `lng` and `precision` directly. `precision` is promoted to a first class field rather than treated as geocoding metadata, because the 4.7 radius query is specified as filtered by coordinate precision, so a radius query that cannot read precision cannot be answered correctly. The two provenance fields the geocoding step produces, `query`, the normalised string actually sent to Photon, and `match`, the string Photon returned, are preserved as well, so the migration from `app/src/data/zonaCoords.json` and `app/src/data/localizacionCoords.json` into `data/records.json` loses no information. Whether `query` and `match` stay in the final model is deliberately left open and decided later, once the database exists and it is clear whether they are read by anything other than a human auditing a coordinate. Precision values in use today are four: `neighbourhood`, assigned in code to records placed from a confirmed zona centroid, and `landmark`, `address` and `street`, assigned per entry by the localizacion geocoding step. This is a statement of the target model, not of the running code, which still joins the two lookup files at runtime.

## 2026-09-04
Database decision, deferred since 2026-08-23, resolved: Postgres with PostGIS, not Firebase. Decided against the query list in `docs/queries.md`, not preference. Reasoning: the flat record modeling decision from 2026-09-03 is neutral between the two, a Postgres row with `lat`, `lng`, `precision` as columns is as flat as a Firestore document with the same fields, so it does not favor Firestore as it first appeared to. The radius query filtered by coordinate precision is listed under "Confirmed, required by checklist item 4.7" in `docs/queries.md`, not under the predicted, unvalidated section, so it is a real requirement even though zona is the primary analysis unit, and it is materially cheaper in PostGIS, `ST_DWithin` with a spatial index, than in Firestore, which needs geohashing, a composite index, and client side post filtering. Count and time-since-last per zona are a wash between the two at the current volume, 15 records. What decided it: the project's learning objective has included SQL and Postgres since before v0.3 started, the project is now a portfolio and technical study rather than a deadline-driven MVP, and this was the standing default since January, never discarded on merit, only deferred until a real query list existed.

## 2026-09-04
Hosting for Postgres decided: Supabase, not local Docker and not a native Windows install. Checked directly rather than assumed: neither Docker Desktop nor a native Postgres install is present on this machine. Reasoning: the project's learning objective is SQL itself, not database server administration, so a local install would add friction unrelated to that goal. Supabase ships PostGIS pre-enabled, closing most of the operational-burden gap that had counted in Firebase's favor during the engine decision above. Running local also sets up a second migration later, from local-only to hosted, if the map or the verification report ever need to be reachable outside this machine, which a hosted start avoids. The free tier covers the current data volume with room to spare.

## 2026-09-07
Concello da Coruna "avisos e incidencias de movilidad" adopted as the second data source, closing Etapa 5 for the MVP. Filtered to physical interventions only, a real cut or works on the street: 2 of the 8 sampled notices kept, ids 032 and 033, and 6 excluded. The exclusions are the reason the filter exists rather than a detail: two bus line changes and one permanent 30 km/h rule dating from 2021 are not incidents at all, and two pedestrianisations are street improvements, so filing them as `urban_damage` would have recorded the opposite of what happened. One street direction change was held out as ambiguous rather than forced into a category. The source is structurally different from the Facebook one and the difference is worth stating plainly: it publishes its own coordinate per notice, so no geocoding is involved, it gives every notice a stable permalink, which satisfies the unique `fuente_url` the "does this post exist" query in `docs/queries.md` depends on, and it has no pagination and no archive. Volume is small by nature, 8 live notices today, a standing register of long running conditions rather than a growing feed like the Facebook group. Field level consequences are recorded in `docs/schema.md` under "Source variations".

## 2026-09-09
Second Apify batch for the Facebook source, fetched via `scripts/fetch-apify.js` against the last successful run of the `apify/facebook-groups-scraper` actor, added: 73 new records, ids 034 to 106, on top of the existing 17. Of 100 posts fetched, 15 were already in the database, deduped by `fuente_url`, leaving 87 new. Of those, 13 were excluded as out of scope for this dataset: 7 job postings including one, id-less, whose OCR revealed a job ad image behind text that looked like a location at first glance, 4 posts with no text and no usable attachment, 2 lost-and-found posts (a bag, an earring) which are neither an item offered nor waste, and one generic recurring donation-drive announcement naming no specific item or place. This leaves 74 with real content, one of which, "en Calle Postas con Avenida Plaza de Toros llevan un tiempo abandonadas" plus an OCR hit of a bicycle, was categorised `bulk_waste` rather than `circular_item`, same reasoning as record 023 in the first batch: phrased as abandoned, not offered.

Scope decided in conversation: unlike the first batch, out-of-A-Coruna-city posts are kept when they appear, first seen here with Culleredo and Oleiros locations. Images are downloaded locally to `data/images/`, same as the first batch, not left on Facebook's CDN, which expires. 4 records placed via a confirmed zona centroid, 3 newly matching Os Mallos and one more Zalaeta. The remaining 69 needed Photon geocoding, which came out far less reliable at this volume than the first batch suggested: sending raw post text produced a 71 percent failure rate and several confident but wrong matches in other regions entirely, Madrid, Valencia, Huesca, another Galician town sharing a street name. Every query was hand cleaned to a bare street or place name, and every successful match was checked against the expected comarca before being accepted, rejecting matches outside it the same way the Puentedeume collision was guarded against in the first batch. Two matches that first looked like false positives, O Burgo and Mera, were accepted after confirming they are real localities inside Culleredo and Oleiros respectively, not different places. 63 of 73 records got a coordinate this way; 10 stayed unplaced with a `reason`, same pattern as id 025.

Applied directly to the live Supabase database via the `execute_sql` MCP tool now available in this session, no SQL Editor copy-paste needed. `db/seed.sql` and `data/records.json` both updated to match, so the flat file stays the record of what is actually in the database, not a partial history.

Observed but not fixed here: record 033 (the Concello batch) has `zona` set to `Os Mallos` but `precision` of `street`, not `neighbourhood`, because its coordinate came from the source's own tag, not a zona centroid. The app's `source` classification in `app/src/data/records.js`, `precision === 'neighbourhood' ? 'zona' : 'localizacion'`, assumed those two facts always travel together, so this record is plotted correctly but counted as `localizacion` sourced rather than `zona` sourced in the map's header stats. Left as a known gap, not corrected in this session.

## 2026-09-09
Basemap changed from CartoDB Positron to Esri Light Gray. Not a preference, the Positron tiles broke: Carto now stamps "API KEY REQUIRED" across its public basemap and still answers HTTP 200 with a valid PNG, checked directly against `https://a.basemaps.cartocdn.com/light_all/13/3969/3062.png`, so nothing errored in the console and the failure was visible only on screen. This supersedes the tile choice made on 2026-09-02, which picked Positron for consistency with v0.2. Esri Light Gray was chosen over plain OpenStreetMap tiles because it keeps the neutral pale canvas the coloured markers are legible against, where the standard OSM style competes with them, and over signing up for a Carto key because that would put a second credential in the browser client for a purely cosmetic layer. It is used as two stacked layers, Base plus Reference, because Esri ships the street labels separately from the label free canvas and this map exists to place incidents on named streets. Tile paths on this service are `{z}/{y}/{x}`, y before x, and take no subdomain placeholder. The tension between a light basemap and the dark UI shell, left open on 2026-09-02, is still open and still not resolved by this change.

## 2026-09-10
Side panel added to the map with two functions, and the standing rule on citizen reporting is replaced rather than bent. The old rule, in `CLAUDE.md`, said citizen reporting stays in the legacy v0.2 flow only. The new rule is narrower and harder: **the dataset is fed by scraping alone**. A citizen submission lands in `public.submissions`, a separate quarantine table defined in `db/submissions.sql`, and never in `public.records`. Nothing crosses from one to the other except by human review, by hand, never automatically. That keeps the v0.3 thesis intact, the value of the dataset is that it is audited and independent of both the operator and unverified public input, while allowing the interface to accept a report again. The 2026-07 pivot away from B2B2C is not reversed: citizen input is not a dependency of the pipeline and must not become one.

The panel's first function is the one that fits the B2B thesis directly. From a record already in the dataset it drafts a formal communication to the Concello, so the audited data turns into something a person can act on. Drafting calls `claude-haiku-4-5` from a Vercel serverless function at `app/api/carta.js`, which holds `ANTHROPIC_API_KEY` server side; the browser never sees a credential. Haiku was chosen over an Opus tier model because the task is a short formulaic letter assembled from structured fields, at roughly a quarter of a cent per draft against about five times that. The prompt forbids inventing streets, dates, names or case numbers, and the panel labels the output a draft and tells the reader to check it, because a plausible wrong street name in a letter to a public body is worse than no letter.

The second function is the report form. Its write path is written against the Etapa 0 failure and the difference is deliberate: `anon` gets `insert` and nothing else, on five named columns of a quarantine table, with `estado` and `promoted_to` withheld so a submitter cannot mark their own row accepted, and no select policy, so the queue cannot be read back from a browser. Verified against the live project rather than assumed: insert returns 201, select returns 401 permission denied. One gap is known and written down rather than left implicit, there is no rate limit, and Postgres alone cannot add one; that needs a captcha, Supabase Auth on the submit path, or an Edge Function in front, and it should be closed before the map is advertised anywhere.

## 2026-09-10, interface language
The interface is Spanish, not English. Everything user facing is translated: header, legend, marker popups, loading and error messages, both panel tabs, the report form and the letter modal. The reasoning is that the users are residents and municipal staff in A Coruna, the data itself is in Spanish and Galician, and the letter the panel drafts has always been Spanish because it is addressed to a Spanish institution. An English shell around Spanish content was the odd part, not the translation. What deliberately stays English: the enum keys stored in Postgres, `illegal_dumping` and the rest, because they are stored values bound by a check constraint in `db/schema.sql` and are not user facing; the field names in `docs/schema.md`; and all code comments and documentation, which are addressed to whoever maintains this. Category labels and their helper text are v0.2's own Spanish, restored verbatim from its `src/data/categories.js` rather than retranslated, so the two versions describe the same six things with the same words.

## 2026-09-10, photo upload
Photo upload carried over from v0.2's `PhotoUpload`, attached to citizen submissions only. Records keep getting their images from the capture pipeline into `data/images/`, that path is unchanged. A submitted photo goes to `submission-photos`, a private Supabase Storage bucket, and its path is stored in a new `submissions.imagen` column. The bucket is written against the same rule as the table: `anon` gets insert and nothing else, so a file cannot be listed, read, replaced or deleted from a browser after upload, and review reads it with the service role key. Limits, 4 MB and images only, are set on the bucket itself rather than in the browser, because a check that only lives in the client is not a control; the check in `app/src/data/submissions.js` exists to fail fast with a readable message. The upload runs before the row is inserted, so a failed upload leaves no row pointing at a file that does not exist. Storage counts against the same Free Plan quota as everything else, 1 GB, and at 4 MB a photo that is roughly 250 submissions before it matters. The rate limit gap recorded on the submissions table applies here too and is now slightly worse, since an unthrottled uploader fills a quota rather than a table.

## 2026-09-10, panel layout
Layout changed to v0.2's: the report form is a permanent sidebar on the left, beside the map, not a panel that has to be opened. The two tab arrangement and the header toggle are removed. The letter is no longer something you go and ask for, it is offered once, in a modal, immediately after a report is submitted, which is the only moment the user has the context to answer the question. The modal has two states, the question and then the letter, so saying no costs nothing and no API call is made.

This supersedes the panel described in the entry above from earlier today, and it drops one thing with it: notifying the Ayuntamiento about a record already in the audited dataset. That path ran through the Notify tab, which no longer exists, and the marker popup has no button for it, so the capability is unreachable from the interface even though `api/carta.js` still supports it, `origen: "record"` is untouched and tested. Restoring it means one button inside the marker popup. It was dropped because it was not asked for in this layout, not because it stopped being a good idea; of the two flows it is the one that matches the B2B thesis, since it turns audited data into something actionable, while the citizen form is the one the 2026-07 pivot moved away from depending on.

## 2026-09-10, address autocomplete
The location field is v0.2's `LocationSearch` autocomplete instead of a free text input, and it resolves through Photon, the same geocoder that placed every record on the map, so a submitted address and a captured one are resolved by the same service. Debounce, minimum query length and the trick of reusing a number the user typed when Photon returns no housenumber are all v0.2's and are kept. The submission now carries `lat` and `lng`, which the free text field could never produce, so a reviewed submission arrives with a coordinate already resolved rather than needing the geocoding pass records go through.

Three things were changed rather than copied, each for a checked reason. First, v0.2 sent a `User-Agent` header on its Photon requests; browsers forbid scripts from setting that header, so it was silently dropped on every request v0.2 ever made, and it is not carried over. Second, the reverse lookup behind "usar mi ubicacion" moves from Nominatim to Photon, so the feature talks to one service. Third, and the one that matters: Photon treats `bbox` as a bias, not a filter. Checked directly, a search for "Rua Tornos 19" returns Os Tornos in **Sada** above Rua Tornos in A Coruna, under v0.2's bounding box and under the tighter one from the capture pipeline alike, so tightening the box fixes nothing. This is the same collision already recorded against record 022. The fix is in the interface: every suggestion shows its municipality on its own line, and A Coruna rows sort to the top, so picking a neighbouring concello by accident requires ignoring the label rather than never seeing it.

## 2026-09-10, coordinate provenance on the map
The marker style was telling a falsehood and is corrected. `sourceFromPrecision()` read only `precision` and routed everything that was not `neighbourhood` to "localizacion", so the two Concello records, whose latitude and longitude are published by the source itself in the page markup and never touch a geocoder, were drawn with the dashed ring the legend describes as deduced from the localizacion string. The discriminator is now `query`, which holds the string sent to Photon and is null on every row that never went through geocoding, so it separates a geocoded guess from a coordinate the source supplied. Three cases exist, not two: `zona` for a bairro centroid, `localizacion` for a geocoded guess, `fuente` for a coordinate the source published. Only the middle one is drawn dashed, and the legend now says "coordenada deducida por geocodificación" rather than describing a precision level, because a centroid and an official point are both exact statements of different things while a geocoded guess is the only one that might be wrong.

The letter about an existing record, which the 2026-09-10 layout change left unreachable, is back as a button inside the marker popup. `CartaModal` and the `useCarta` hook moved out of `ReportSidebar` so the map and the sidebar share one implementation, and the modal still asks before spending anything. The "Etapa 3 / mapa mínimo" label is gone from the header; the staged build plan it referred to is finished and the label had been wrong for two stages.
